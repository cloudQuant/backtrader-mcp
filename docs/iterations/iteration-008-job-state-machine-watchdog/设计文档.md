# 迭代 008：作业状态机硬化与监督闭环设计

## 架构决策

1. **CAS 在事务内**。`StateStore.update` 的 `expected` 前置条件与读-改-写共用
   `BEGIN IMMEDIATE` 事务：前置条件失败回滚并抛 `Conflict`。所有作业状态写入
   （worker 侧、cancel、get_run_status、watchdog、恢复）显式声明允许的前置状态。
2. **仲裁规则**（单一权威，写入方各自遵守）：
   - 终态（CANCELLED/SUCCEEDED/FAILED/TIMED_OUT/ORPHANED）一旦持久化永不被覆写；
   - CANCEL_REQUESTED 一旦可见，SUCCEEDED/FAILED/TIMED_OUT 写入失效；
   - CANCELLED 的写入前置条件是 `state == CANCEL_REQUESTED`——cancel 与 worker
     谁先 CAS 成功谁写终态，另一方读到最终状态返回。
3. **watchdog 是服务器职责**。守护线程只在 `run_stdio`（serve）创建：服务先于
   server 构造（新增 `create_server(settings, service=...)` 可选参数），
   watchdog 随 stdio 循环结束而停止。CLI 命令不启动 watchdog、不产生额外副作用。
4. **拒绝而非排队**。并发闸门用全局 flock 串行化"计数+创建"，超额抛 Conflict
   并附可操作建议；不实现 FIFO 队列（README 文档化）。
5. **error_kind 是诊断契约不是状态机**。新增 job 字段 `error_kind`，分类规则
   单一来源：worker 的 `_classify_exit()` 纯函数 + 各写入点的显式赋值；不新增
   作业状态。

## 接口契约

- `StateStore.update(kind, object_id, mutator, *, expected=None)`：
  expected 为 `Callable[[dict], bool]`，False → `Conflict(f"{kind} precondition
  failed: {object_id}")`，不写库。
- `worker._write_terminal(state_store, job_id, state, error, error_kind)` →
  `dict | None`：前置条件 `state not in TERMINAL_STATES and state !=
  "CANCEL_REQUESTED"`；Conflict 时返回 None（调用方按"已被终态/取消"处理）。
- `worker._classify_exit(returncode)` → `(kind, detail) | None`：
  负数 → `("resource_limit", f"killed by signal {signal.Signals(-rc).name}")`；
  正数 → `("user_strategy", ...)`；0 → None。
- `JobService.start_watchdog()` → `JobWatchdog`（`stop()` 可 join）；
  `watchdog_tick()` 返回 `{"enforced": [...]}`，可单测。
- 模块常量：`HEARTBEAT_STALE_SECONDS = 15.0`、`WATCHDOG_INTERVAL_SECONDS = 2.0`、
  `WATCHDOG_DEADLINE_GRACE_SECONDS = 5.0`。
- `JobService.clean_jobs(before_iso)` → `{"deleted_rows": n, "removed_dirs": m}`。
