# 迭代 005：发行版本一致性

## 1. 背景与问题

迭代 004 的最终复审发现版本标识已发生漂移：pyproject.toml、MCP server 和 service
product info 使用 0.2.0，而 backtrader_mcp.__version__ 与 doctor 测试中的发行包 mock
仍为 0.1.0。doctor 从 __version__ 读取版本，因此用户会在真实 wheel/CLI 上看到与
安装元数据、MCP initialize 元数据不一致的产品版本。

这不是展示问题：安装脚本、宿主兼容性记录和故障报告会以该值关联发行物，版本不一致会降低
可追溯性。

## 2. 目标

- 令构建元数据、Python package、MCP server、service product info 和 doctor report 统一为
  一个权威的 0.2.0 版本。
- 使用 Hatchling 的公开 dynamic = ["version"] 加 tool.hatch.version.path 配置，使 wheel
  构建从 package __version__ 获取版本，避免下一次复制值再次漂移。
- 修正 README 中还指向 0.1.x / 0.1.0 的升级说明，并由 wheel 与回归测试证明安装后的
  metadata 和运行时值一致。

Hatch 官方文档定义了 dynamic = ["version"] 与 tool.hatch.version.path 的组合，并说明
默认 regex source 从 __version__ 或 VERSION 读取版本：
[Configuring project metadata](https://hatch.pypa.io/latest/config/metadata/)、
[Versioning](https://hatch.pypa.io/dev/version/)。

## 3. 范围

### 包含

- pyproject.toml、src/backtrader_mcp/__init__.py、service.py、server.py 的版本单一
  来源改造；
- doctor、service、MCP server 与 wheel metadata 的回归测试；
- README、CHANGELOG 与本目录三份文档的发行说明同步；
- 全量、公开 Backtrader runtime、clean-room wheel 验收。

### 不包含

- 发布到 PyPI、升级到 0.2.1、修改 schema/API version、迁移已有 state，或改变 MCP SDK
  兼容范围；
- 仅把所有常量批量替换成另一个硬编码值而不消除构建/runtime 的重复来源。

## 4. 功能需求

| ID | 需求 | 优先级 |
| --- | --- | --- |
| R1 | 构建配置必须声明动态 version，且唯一读取 src/backtrader_mcp/__init__.py 的 __version__。 | P0 |
| R2 | BacktraderMCPService.product_info()、MCP server 的 initialize version、doctor report 必须使用 package __version__，不得各自硬编码。 | P0 |
| R3 | 所有发行向文档使用 0.2.x / 0.2.0 的正确语义；不留误导升级者的 0.1.x 或 0.1.0 声明。 | P1 |
| R4 | wheel 的 .dist-info/METADATA 版本、安装后 backtrader_mcp.__version__ 和运行时 product info 必须均为 0.2.0。 | P0 |
| R5 | 现有 80% coverage gate、14 格矩阵、协议和独立性验收不得退化。 | P0 |

## 5. 完成定义

1. 开发前存在本需求、设计、验收文档；
2. 先存在失败测试，证明当前 doctor/package 或构建 metadata 的版本漂移；
3. 构建的 wheel、installed package 和三种 runtime surface 都返回相同的 0.2.0；
4. Ruff、受 MCP 2.0.0 target 验证的 mypy、全量 suite、public runtime、clean-room wheel
   均通过；
5. 复审不存在第二个未绑定到 __version__ 的 product release version 常量。
