# 迭代 002：设计文档

## 1. 声明策略 import 与可信 harness 的分层

`StaticValidator` 接受一个可选的 `allowed_strategy_imports` 集合。`DraftService` 从
已冻结的 canonical StrategySpec 传入该集合；独立调用 `validate_sources()` 时保持现有
全局安全 allowlist，供低层测试和工具使用。

- `strategy.py` 只允许 `allowed_strategy_imports` 中的模块。
- `run.py` 与 `test_strategy.py` 是产品生成的 harness，除 strategy 声明外固定允许
  `json`、`os`、`pathlib`；`backtrader_mcp.feed_runtime.run_materialized_backtest` 仍只
  能以现有专用 import 规则导入。
- 禁止项、环境键、结果路径和 live-trading 检查不变。报告 evidence 新增实际策略
  allowlist，便于复核 validation hash 所代表的策略约束。

这使 `allowed_imports` 从“已哈希但无效的元数据”变为草稿校验输入，同时保留 runner
最小能力集。

## 2. run profile 与声明模式

定义单一常量映射：

| run profile | 实际执行模式 |
| --- | --- |
| `runonce` | `runonce` |
| `runnext` | `runnext` |
| `runonce_runnext_compare` | `runonce`, `runnext` |
| `fixed_tests` | `runonce`, `runnext` |

`prepare_strategy_run` 取得 `StrategySpec.run_modes` 后，要求 profile 需要的每一个模式
都已声明；否则在生成 run token 前抛出 `InvalidRequest`。plan 同时保留
`declared_run_modes` 与 `execution_modes`，并把 `execution_modes` 写入 run manifest。
worker 只消费冻结的 `execution_modes`，并验证它是所选 profile 的确定映射，避免执行时
由另一个映射重新推导。

默认 spec 仍声明两种模式，现有 fixed-tests 行为不变。只有显式单模式 spec 在请求需要
双模式的 profile 时会被确定性拒绝。

## 3. clean-room wheel acceptance

```mermaid
flowchart LR
    A[build product wheel] --> B[pip install wheel[test] into temporary target]
    B --> C[probe installed origin and dependency versions]
    C --> D[fixed 14-cell matrix]
    C --> E[wheel contents and clean catalog test]
    C --> F[MCP 2.0 protocol test]
    D --> G[structured acceptance JSON]
    E --> G
    F --> G
```

脚本把 wheel 加上 `[test]` extra 安装到 `installed_target`，并以该目录作为唯一
`PYTHONPATH` 前缀。安装命令使用仓库的 MCP/Pandas constraints；wheel metadata 中的
test extra 固定 Backtrader 版本。探针用 `importlib.metadata.version()` 记录并要求：

- `backtrader==1.9.78.123`；
- `mcp==2.0.0`；
- `backtrader_mcp` 的模块 origin 位于 `installed_target`；
- 源 checkout、Skills、Agent 不在执行 import 路径。

`tests/test_protocol_v2.py` 与 matrix/wheel tests 由同一 temporary target 运行。任一
子验证失败都写入 JSON 尾部并使脚本退出非零。

matrix 为每个 candidate 明确请求 60 秒的 product run timeout；`_wait()` 则使用 75 秒的
测试侧终态观察窗口，给 worker 写回 terminal state 留出余量。通用测试 fixture 的
`max_run_seconds` 上限为 90 秒，因此它仍是有限的测试安全边界、同时允许这项 60 秒计划。
这样首次从 clean-room target 导入 NumPy/Pandas/Backtrader 的冷启动不会被测试传入的 25 秒
timeout 误判；真正卡住的 candidate 仍由其 60 秒 product timeout 标为 `TIMED_OUT`。这不
改变产品配置允许的 `max_run_seconds`（默认 300 秒）。

## 4. MCP 兼容范围

将 project dependency 和 `product_info().mcp_sdk` 收窄为 `>=2.0.0,<2.1`。这是基于
当前 SDK API 的实际协议测试，而不是推断未来 minor/major 兼容。constraints 继续锁定
`mcp==2.0.0`，因此 CI 和 clean-room acceptance 具有同一运行时。

## 5. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 生成 harness 被错误当作用户 import 而拒绝 | 将 harness 最小 import 与 strategy allowlist 分层，并回归全部十四个 scaffold。 |
| 单模式 profile 的结果缺少 comparison | 仅单模式 profile 允许；比较 profile 在 prepare 阶段要求两种声明模式。 |
| 临时 target 安装耗时增加 | 只在 distribution acceptance 使用；换取不依赖宿主包的可复现证据。 |
| SDK 版本范围收窄影响未验证用户 | 这是诚实的兼容声明；未来新增版本须先补 CI/protocol 证据再放宽。 |
