# 迭代 002：执行声明闭环与 clean-room 分发验收

## 1. 背景与问题

迭代 001 已修复已发布字段丢失、公开 Backtrader adapter 兼容性和基础 CI 门禁，并在
PyPI `backtrader==1.9.78.123` 下完成十四格运行验证。复审仍发现以下 P1 缺口：

1. `StrategySpec.allowed_imports` 会被 parser 保存并纳入 `spec_hash`，但草稿 AST
   validator 固定使用全局 import allowlist，未读取该声明。声明较窄的 spec 仍可通过
   额外的全局允许 import，导致 hash 中的策略约束不是实际校验约束。
2. `StrategySpec.run_modes` 同样会被保存和冻结，但 `prepare_strategy_run` 不校验所选
   run profile 是否只执行已声明模式；worker 会按 profile 执行，可能运行 spec 未声明的
   `runnext` 或 `runonce`。
3. `scripts/run_acceptance.py` 将 product wheel 以 `--no-deps` 安装到临时 target，
   却依赖调用机已有的 pytest、MCP、Pandas 和 Backtrader。它在开发机上实际使用
   Backtrader 1.2.0 仍可通过，不能单独证明 test extra 固定的公开
   `backtrader==1.9.78.123`。
4. 项目 metadata 声明 `mcp>=2.0.0,<3`，但当前唯一受约束且实际验证的 SDK 是
   `mcp==2.0.0`。没有证据可将整个 2.x 世代视为兼容。

## 2. 目标

- 让 `allowed_imports` 成为草稿静态校验的有效上限，同时不破坏产品自有 runner 所需的
  `json`、`os`、`pathlib` 与可信 `feed_runtime` import。
- 让 run profile 的实际执行模式必须是 StrategySpec 声明模式的子集；在准备阶段失败，
  而不是在审批后或运行中才出现不一致。
- 让 wheel acceptance 自行从构建的 wheel 安装 `.[test]` 依赖闭包到临时 target，并在
  该 target 中运行固定十四格矩阵、wheel 内容检查和 MCP v2 protocol 测试。
- 依据已有证据将 MCP runtime 兼容范围限制为已验证的 2.0.x，而不夸大为全部 `<3`。

## 3. 范围

### 包含

- `DraftService`、AST validator、`JobService`、worker 的声明/执行模式边界。
- `scripts/run_acceptance.py` 的临时依赖安装、结构化输出和 protocol 测试。
- `pyproject.toml`、wheel metadata 测试、README、CONTRIBUTING、CHANGELOG 和 CI 中的
  MCP 兼容范围同步。
- 每项行为的正向和拒绝回归测试，以及本目录下三份迭代文档与验收证据。

### 不包含

- 开放任意用户 Python import、网络 transport、实盘交易或扩展 StrategySpec v1 的
  public 字段。
- 对 Windows 的新进程组/资源限制实现；当前自动化支持边界继续是 Linux/macOS，是否扩展
  Windows 另立需求与实际环境验收。
- 仅为提高数字而扩大 coverage omit 或降低已有安全限制。

## 4. 功能需求

| ID | 需求 | 优先级 |
| --- | --- | --- |
| R1 | 草稿静态校验必须从已冻结 `StrategySpec.allowed_imports` 取得 strategy import 上限；未声明但全局可用的 import 必须拒绝。 | P0 |
| R2 | `single_test`/`python_bundle` 自有 harness import 必须保持可用，但不能借此放宽策略源代码的声明上限。 | P0 |
| R3 | 每个 fixed run profile 定义确定的执行模式；`prepare_strategy_run` 必须拒绝要求未包含在 `StrategySpec.run_modes` 中的 profile。 | P0 |
| R4 | 成功的 run plan/run manifest 必须能复查声明模式和该 profile 实际执行的模式，worker 不得重新推导出不一致的集合。 | P1 |
| R5 | clean-wheel acceptance 必须从 wheel 的 `[test]` extra 安装所有测试/runtime 依赖到临时 target；不得依赖宿主 Python 的 Backtrader/MCP/Pandas。 | P0 |
| R6 | clean-wheel acceptance 必须记录并断言临时 target 中的 Backtrader/MCP 版本，并运行 MCP v2 protocol 测试。 | P1 |
| R7 | 分发 metadata、产品信息、文档与 wheel 测试必须一致声明 `mcp>=2.0.0,<2.1`。 | P1 |
| R8 | 十四格 acceptance matrix 的测试侧终态观测窗口必须覆盖 clean-room 首次导入的冷启动开销，并仍大于产品实际 run timeout；不得把未完成作业误报为产品失败。 | P1 |

## 5. 完成定义

1. 先有本轮需求、设计和验收文档，再有对应实现；
2. 窄 `allowed_imports` 拒绝额外 import，显式声明的 import 通过，所有 fourteen
   scaffold 仍通过；
3. 单模式 StrategySpec 可运行匹配的单模式 profile，`fixed_tests` / comparison profile
   对缺少模式在 prepare 阶段失败；
4. clean-room 脚本的 wheel 安装、14/14 矩阵、wheel 内容、独立性和 protocol 均通过，
   输出包含实际依赖版本和 installed-origin 证据；
5. Ruff、required mypy、相邻源码及公开 PyPI Backtrader 的完整 suite 都通过；
6. 复审没有发现同等级的声明/执行失配或分发验收依赖宿主环境的问题。
