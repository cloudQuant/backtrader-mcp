# 迭代 001：P0 契约正确性与可执行质量门禁

## 1. 背景与问题

`backtrader-mcp` 是一个本地优先、离线回测的 MCP 产品。其安全、可复现和
独立分发承诺只有在每次变更都能由一个干净环境重复验证时才成立。

2026-08-02 的只读基线审计确认了以下问题：

1. `.github/workflows/ci.yml` 的 typing job 使用 `continue-on-error: true`，而
   当前 `mypy` 在 11 个源码文件中报告 18 个错误；主分支可以在类型检查失败时
   仍显示 CI 通过。
2. 仓库同时使用 Black 和 Ruff formatter：CI/贡献指南使用 Black，Ruff formatter
   对四个已跟踪文件报告不同的格式结果。格式化的唯一事实来源不明确。
3. 测试夹具默认依赖本机相邻的 Backtrader 源码目录；CI workflow 没有安装测试
   所需的 Backtrader 运行时，也没有显式覆盖运行时根路径。因此干净 checkout 的
   测试前提不完整。
4. README、CONTRIBUTING 和 CHANGELOG 把覆盖率门槛描述为 80%，但
   `pyproject.toml` 实际只强制 75%。发布文档与执行门禁不一致。
5. `scripts/run_acceptance.py` 已能构建 wheel、从 checkout 外 clean-install、运行
   14 格矩阵并验证 product independence，但 CI 从未调用该脚本；当前 CI 对分发
   证据只覆盖源码测试。
6. `strategy-spec.schema.json`、CHANGELOG、scaffold 和运行器都声明/使用顶层
   `slippage`，但 `StrategySpec.parse()` 的 canonical field allowlist 漏掉该字段。
   因此合法策略会被拒绝，且 `parse(as_dict())` 不能往返。
7. parser 虽允许 schema 发布的 `extensions`、`ir`、`non_goals` 和 `undecided`，却
   未保存到 canonical output 或 `spec_hash`。同时多数据源运行所需的 `dataset_feed`
   只被隐藏地消费，公开 schema 不允许它，canonical output 也会丢失它。这破坏了
   对可复现输入和向后兼容 extension 的承诺。
8. 在隔离环境中以 test extra 声明的公开 PyPI `backtrader==1.9.78.123` 运行十四格
   矩阵时，`BacktraderCSVData`、`YahooFinanceCSVData` 和 `MT4CSVData` 会拒绝
   `io.StringIO` 作为 `dataname`；现有本地相邻 fork 没有暴露这个差异。测试 extra
   既声明支持公开运行时，就必须让受控 CSV adapter 在该运行时可执行，不能只在
   本地 fork 上通过。
9. 同一公开运行时中，`multi_indicator_system` 的 `RSI` 在单调上涨或初始化窗口无
   负收益时会触发除零；本地 fork 未复现。模板必须使用公开 Backtrader 提供的安全
   RSI 变体，保证 runonce 与 runnext 都能产出可比较结果。

## 2. 目标

建立一个能在干净 Python 环境中重复执行、并且失败即阻断合并的质量门禁：

- 让已发布的 StrategySpec 字段在 schema、解析、canonical output、哈希、scaffold
  与运行时之间完整闭环，特别是 `slippage`、扩展元数据和 `dataset_feed`。
- 测试 extra 提供一个明确、受约束的 Backtrader 测试运行时；产品运行时依然由
  用户在配置中显式注册，不能变成生产依赖。
- 测试运行时解析顺序可预测：显式环境变量、相邻源码 checkout、已安装的
  Backtrader 包；每个候选都必须含有 `backtrader/__init__.py`。
- 使用 Ruff 作为唯一格式化器，避免 Black 与 Ruff 的双重且可能分歧的判断。
- 修复当前 mypy 错误，并把 typing 从 advisory job 变为 required job。
- 在 Linux CI 中执行独立 wheel acceptance，并保留其 JSON 结果作为失败时的诊断
  工件。
- 以实测覆盖率为准：若完整套件达到至少 80%，将配置门槛提升至 80%；若未达到，
  先补充针对未覆盖产品逻辑的测试，再提高门槛。所有用户文档必须与最终门槛一致。

## 3. 范围

### 包含

- `pyproject.toml`、CI、pre-commit 与贡献文档中的质量门禁统一。
- `StrategySpec` 字段保留、schema/parser parity 及其回归测试。
- 测试夹具的运行时发现和失败信息。
- 为类型修复、运行时发现和覆盖率门槛新增或调整的测试。
- CI 中的 clean-wheel acceptance job 与其结构化证据工件。
- 公开 PyPI Backtrader 1.9.78.123 下 CSV adapter 的兼容构造与临时文件清理。
- `multi_indicator_system` 在零损失窗口上的安全 RSI 模板行为与回归覆盖。
- 仅为解决本轮 mypy 问题所需的最小源码类型标注/收窄改动。
- 本目录下需求、设计、验收文档和实施后的证据记录。

### 不包含

- 网络 MCP transport、实盘交易、券商、密钥或任意代码执行能力。
- 将 Backtrader 加入产品的运行时 `dependencies`。
- 修改策略、数据 CAS、审批、运行执行语义，除非类型修复证明现有行为错误。
- 依赖真实 Claude/Codex/OpenClaw 会话作为本轮的自动化验收前提。

## 5. 完成定义

本迭代完成的必要条件：

1. 本轮文档、实现和测试均已落盘；
2. `ruff check`、`ruff format --check`、required `mypy`、完整 pytest（含覆盖率）和
   独立 wheel acceptance 全部通过；CI 也声明并执行相同的 wheel acceptance；
3. CI 配置不再包含对本轮 typing 失败的容忍；
4. 测试 extra 与干净环境运行时解析均有自动化证据；
5. `slippage`、可选元数据和非默认 `dataset_feed` 的
   schema/parser/serializer/hash/scaffold/运行时链路有自动化回归证据；
6. 公开 PyPI `backtrader==1.9.78.123` 环境中的十四格矩阵为 14/14，且 adapter
   临时文件无泄漏；
7. 后续复审没有发现同等级的质量门禁或已发布契约缺口。
